Game Engine

Abstract

A game engine is

"a software framework primarily designed for video game development, which may include specialized software libraries and packages"

It usually is a wrapper for many other engines like graphics engine, physics engine, audio engine, animation engine, etc... combined to make development easier and self-sustained. Thus, developing a game engine is developing multiple sub-engines that can talk and interact with each other in different ways.
Due to the proprietary licenses that are applied to big engines like Unity, Unreal, etc... much of the underground work is already done and prepackaged for us to use. But simply using something doesn't mean we know how it works. Additionally, the licenses are heavily in favor of the companies, in respect to the little you gain from developing on their software. Big gamedev studios have already developed their own game engines in order to maximize profits and avoid third parties altogether .
This is why many choose to build their own game engines from scratch, like a challenge or simply for fun. And this is the basic concept behind the development of this game engine. The objective is to develop a fully functional software that is able to deliver high-end games with as much functionality it can produce, all while learning the core principles that make a game engine a game engine.

Structure

Before we begin, there are some ground rules we need to give ourselves. Game engines are usually of two types:

  • Software engines: they basically allow the user to build the game from a window, using buttons and mainly the mouse to do everything (e.g. Unity, Unreal, etc...)
  • Library engines: they are libraries which are included in the code for the game that give core functionalities to create a window, render images or text, etc...
The game engine that this paper is going to present is the latter, thus we will build from scratch the core functionalities that allow us to create a basic game, that can be later expanded to a fully-fledged game engine for AAA games.
We're going to be using Simple DirectMedia Layer 2 as our boilerplate for basic window and image rendering. Also, there is another goal in mind: develop the final product using the least amount of external libraries possible. Since we're working with C++, the only libraries I've allowed myself to use are <stdio>, <stdlib>, <string> and <cmath>.

    [✓] [custom message]

Engines

As we said, a game engine is a wrapper for multiple engines. The main ones we will develop are:

  • Graphics engine: the base of everything, it will allow us to see what we're doing in real time displaying objects to a custom window.
  • Physics engine: deals with rigidbody physics, forces and everything else.
  • Audio engine: deals with the audio files, adding reverb, spatial, etc...

Graphics Engine

The basic functionality of any game engine, or at least any software dealing with User-Interfaces (UI), is displaying things onto the screen. Starting out, we need a window:

"In computing, a window is a graphical control element. It consists of a visual area containing some of the graphical user interface of the program it belongs to and is framed by a window decoration."
Since we're using SDL2, an opaque type for a window is already given to us as SDL_Window. This will be our main window for anything, thus we just need to initialize it following the functionalities of SDL2: 
void create_window(SDL_Window*& window, const char* title, int x, int y, 
			int width, int height, Uint32 flags) {
	window = SDL_CreateWindow(title, x, y, width, height, flags);
		if (!window) {
		sdl_error("window.cpp > Window couldn't be created");
	}
	message("Window has been created");
	SDL_SetWindowResizable(window, SDL_FALSE);
}
void destroy_window(SDL_Window*& window) {
	if (!window) {
		warning("window.cpp > Window already destroyed...");
	} else {
		SDL_DestroyWindow(window);
		window = NULL;
	}
}
This is how the window is created/destroyed inside the engine. We pass it a SDL_Window object, and it automatically creates the window, sets it non-resizable ad handles its destruction in a memory-safe way. What we obtain is a window being created on the screen with a title, at an \( (x,y) \) position with \( width \times height \) dimension.

Fig 1. Empty window created

Now that we have a window, we need to create a renderer:
"In a computer graphics context, in standard usage, the word rendering by itself means rendering 3D scenes,but it is sometimes used with a broader meaning. A modifier such as "2D" or "3D" is used when there is potential ambiguity."
Thus, a renderer allows us to effectively draw something onto the window, that we can now refer to as a canvas. SDL2 gives us the SDL_Renderer object which we can pass into the engine's initializer void create_renderer(SDL_Window* window, SDL_Renderer*& renderer) or destroyer void destroy_renderer(SDL_Renderer*& renderer): 
#include <SDL2/SDL.h>

#include "../../misc/include/log.hpp"
#include "../../misc/include/colors.h"
#include "include/renderer.h"

void create_renderer(SDL_Window* window, SDL_Renderer*& renderer) {
	// Use VSync and hardware acceleration on render
	renderer = SDL_CreateRenderer(window, -1, SDL_RENDERER_PRESENTVSYNC | SDL_RENDERER_ACCELERATED);
	if (!renderer) {
		sdl_error("renderer.cpp > Renderer couldn't be created");
	}
	message("Renderer has been created");
	// Set background to black
	SDL_SetRenderDrawColor(renderer, C_BLACK.r, C_BLACK.g, C_BLACK.b, C_BLACK.a);
	SDL_RenderClear(renderer);
}


void destroy_renderer(SDL_Renderer*& renderer) {
	if (!renderer) {
		warning("renderer.cpp > Renderer already destroyed...");
	} else {
		SDL_DestroyRenderer(renderer);
		renderer = NULL;
	}
}

We create the renderer through the SDL_CreateRenderer function, and we set the background to black before clearing the screen. When we want to destroy it, we simply use another function, the SDL_DestroyRenderer, and set to NULL its pointer.
Since the renderer isn't a static object, we also do have some functionalities connected to it, such as:
  • void renderer_update(SDL_Renderer* renderer): updates the renderer.
  • void renderer_clear(SDL_Renderer* renderer): clears the renderer.
Like so: 
void renderer_update(SDL_Renderer* renderer) {
	SDL_RenderPresent(renderer);
}

void renderer_clear(SDL_Renderer* renderer) {
	// Clear the previous frame to black
	SDL_SetRenderDrawColor(renderer, C_BLACK.r, C_BLACK.g, C_BLACK.b, C_BLACK.a);
	SDL_RenderClear(renderer);
}

Now, when we present data to be displayed onto the screen — hence why it's called SDL_RenderPresent — we can't just let the pixel stay on the screen, otherwise movement will seem duplicated:

Fig 3. Avoiding clearing frame buffer

After every rendering of a frame, we need to clear the frame buffer to display correctly the next frame. To do so, we use renderer_clear(), that will clear the screen by putting all black pixels inside the buffer:

Fig 4. Clearing frame buffer

The only problem now is when to call each function...
When we begin drawing, the GPU receives data in, and outputs a stream of pixels. Most screens use a frame buffer that stores the individual calculated pixels until a full frame is produced. One everything is set, it's sent to the screen, an each pixel is drawn from the top-left corner to the bottom-right corner of the screen (a technique called "progressive scanning") many times per second, a period of time called frame rate:
Kadano, CC BY-SA 3.0, via Wikimedia Commons

Fig 2. Progressive scanning of pixels

The faster the frame rate, the more fluid the movement: for example, eyes render images and simple movements in a \( 30 \)-\( 60 \) frames per second interval (time it takes light to be processed inside the eye, the image sent to the brain, and the processing of it inside the brain), so matching it or even surpassing it makes everything smoother.
Basically, if we can calculate the time between each refresh, we have the exact window of time to call the refresh and present pixel functions. That interval is the time \( t \) elapsed from when we start drawing to when we end drawing — calculated like \( t_{final} - t_{start} \) — is called \( \Delta t \) or delta time.
If we don't use the delta time, our game loop will present pixel data and clear the screen as fast as it can run, which is not optimal and will consume a lot of resources. Using it, we can make our code run exactly in time with the screen refresh rate: 
float delta_time;
int delay = 1000;

float calculate_time(Uint64 start) {
	return (float)(SDL_GetTicks() - start);
}

void cap (Uint64 start, int max) {
	delta_time = (float)((SDL_GetTicks() - start) * 1000 / (double)SDL_GetTicks());
	if ((delay / max) > (SDL_GetTicks() - start)) {
		SDL_Delay((delay / max) - (SDL_GetTicks() - start));
	}
}

Let's go through this step by step:
  • Line 4 - Line 6: the function calculate_time() takes in a starting point in time, and returns the elapsed time using the SDL_GetTicks(), basically using the delta time formula.
  • Line 8 - Line 13: we define a capping function, which means it will delay our run time in case we're going faster than we should. Firstly, we calculate the delta time, then check if \( \frac{delay}{max} > \Delta time\). In case it's true, we use SDL_Delay() by the amount of time we're skipping.
Now that we have the base to display stuff to the screen, we can proceed to dimension-specific rendering.

2D Graphics Engine

A two-dimensional space is a mathematical space with two dimensions (duh), which we can represent using the Euclidian plane \( \mathbb E ^2 \). On it, we use the Cartesian coordinate system, thus obtaining a Cartesian plane, where every position is denoted using two real numbers in pair, that determine the offset from the origin at \( (0,0) \). The horizontal axis is called ordinate or \( x \) axis, meanwhile the vertical axis is called abscissa or \( y \) axis, and these two divide the plane in \( 4 \) quadrants.

Kbolino, Public domain, via Wikimedia Commons

Fig 5. Cartesian coordinates

These notions are necessary to understand where objects will appear based on the positions we will give them. By default, every window of every operating system has the origin at the top-left corner, so we're working with the bottom-right quadrant (thus \( x \) is always positive, meanwhile \( y \) will increase the further down we go).
Now that we understand how to represent position, we can simplify our lives talking about vectors in Euclidian geometry:
"[...] A Euclidean vector, or simply a vector [...] is a geometric object that has magnitude (or length) and direction. Euclidean vectors can be added and scaled to form a vector space. [...] A vector is frequently depicted graphically as an arrow connecting an initial point \( A \) with a terminal point \( B \), and denoted by \( \overrightarrow{AB} \)"
Thus a vector holds two points, like this: \( \begin{bmatrix} a \\ b \end{bmatrix} \). While vectors are mainly used with matrices and scalars (which we'll talk about later with 3D graphics), they also serve another function: they store two values. Where do we need to access two numbers in pair to represet something? That's right, a vector can be used to represent a point in the plane like \( (a, b) \). Thus, we can create the Vector2D class to handle vectors in 2-dimensions: 
class Vector2D {
	public:
		double x;
		double y;
		
		Vector2D(double x_pos, double y_pos);
		
}

This class creates a vectors object, whose constructor is Vector2D(double x, double y). Since the values are public, we can reference them easy in the code like so: 
Vector2D position = new Vector2D(150, 150);
std::cout << "(" << position.x << ", " << position.y << ")" << std::endl;
// "(150, 150)"

Now that we have the tools to represent a point in Euclidian space, we can use it to build the next block of our graphics engine, something so important it wouldn't be a graphics engine without: shapes.

Polygons

The fundational block of every graphic design is the simple shape. Every videogame ever created, even "Tennis for Two" (the first ever video game), had the most basic shapes ever. Basically, if we want to create a real graphics engine, we need to add shape rendering.
Thankfully, SDL2 already has built-in functions to render shapes, or as we should call them geometrically polygons, so we can build functions around them to facilitate coding them in the game: 
#include <SDL2/SDL.h>

#include "../../core/misc/include/log.hpp"
#include "include/polygons.h"
#include "include/vector2d.hpp"

void rect(SDL_Renderer* renderer, Vector2D pos, int w, int h, SDL_Color fcolor, bool filled) {
	SDL_Rect rect;
	rect.x = pos.x;
	rect.y = pos.y;
	rect.w = w;
	rect.h = h;
	SDL_SetRenderDrawColor(renderer, fcolor.r, fcolor.g, fcolor.b, fcolor.a);
	if (filled) {
		SDL_RenderFillRect(renderer, &rect);
	}
	SDL_RenderDrawRect(renderer, &rect);

}

void point(SDL_Renderer* renderer, Vector2D pos, SDL_Color fcolor) {
	SDL_SetRenderDrawColor(renderer, fcolor.r, fcolor.g, fcolor.b, fcolor.a);
	SDL_RenderDrawPoint(renderer, pos.x, pos.y);
}

void line(SDL_Renderer* renderer, Vector2D pos1, Vector2D pos2, SDL_Color fcolor) {
	SDL_SetRenderDrawColor(renderer, fcolor.r, fcolor.g, fcolor.b, fcolor.a);
	SDL_RenderDrawLine(renderer, pos1.x, pos1.y, pos2.x, pos2.y);
}

void connect(SDL_Renderer* renderer, Vector2D point1, Vector2D point2, SDL_Color fcolor) {
	line(renderer, point1, point2, fcolor);
}
This piece of code renders a rectangle, point, line and a special function that will help us when dealing with 3 dimensions further down the road, the connect.

For now, we will consider that every image passed into the engine is a PNG raster image, so let's ignore every other possible type, such as vector images and such.
SDL, as always, has a way to display image data onto a screen, but it's not as straightfoward as the polygons.
An image is composed of 2 elements:
  • Surface: a collection of pixels used in software blitting.
  • Texture: a representation of pixel data.
So to effectively render an image inside a window, the SDL library creates a surface, that extracts pixels from an image and stores them in memory, until a texture of that surface is created. Once we have the texture, we can add it to the renderer to be rendered onto the screen. An implementation of the class Image would look something like this: 
#include <SDL2/SDL.h>

#include "vector2d.hpp"
#include "../../../core/misc/include/colors.h"

void init_img(int flags);

class Image {
	private:
		const char* path;
		SDL_Texture* texture = NULL;
		SDL_Renderer* i_renderer;
		SDL_Rect rect;
		Vector2D position;
		int w;
		int h;
		SDL_Point center;
		SDL_Color color;
	
	public:

		Image(SDL_Renderer *renderer, const char* image_path, const Vector2D& pos, 
			int width = 0, int height = 0, SDL_Color i_color = C_WHITE) noexcept;
		~Image() noexcept;

		void render() const;
};

void close_img();

Firstly, let's initialize a special library of SDL to work with images: SDL_image.h. After that, an image is declared by its constructor, taking in a renderer, the path as a string to the file, the position to be rendered to, a width and a height, and an eventual color. Naturally, we might not want to render all images at once, so we specify a render() function.
Let's see how to effectively implement the image: 
#include <SDL2/SDL.h>
#include <SDL2/SDL_image.h>

#include <string>
#include <cstdlib>

#include "../../core/misc/include/log.hpp"
#include "../../core/misc/include/colors.h"
#include "../../src/misc/include/resources.h"
#include "include/vector2d.hpp"
#include "include/image.h"

void init_img(int flags) {
	if (IMG_Init(flags) == 0) {
		sdl_error("image.cpp > Couldn't initialize SDL_Image");
	}
	message("SDL_image initialized successfully");
}

The main flag we will use is the IMG_INIT_PNG to work with PNGs. Now that we have initialized the library, we can finally define what an image is to the game engine: 
Image::Image(SDL_Renderer *renderer, const char* image_path, const Vector2D& pos,
			int width, int height, SDL_Color i_color) noexcept {
	// Use the resource manager to get surfaces and create textures efficently
	texture = SDL_CreateTextureFromSurface(i_renderer, get_surface(path));
	if (w > 0 && h > 0) {
		rect.w = w;
		rect.h = h;
	} else if (w == 0 && h == 0) {
		SDL_QueryTexture(texture, NULL, NULL, &rect.w, &rect.h);
	} else {
		error("image.cpp > Incorrect usage of width/height measures");
	}
	rect.x = position.x;
	rect.y = position.y;
	center = {w / 2, h / 2};
	SDL_SetTextureColorMod(texture, color.r, color.g, color.b);
}
Now let's go step by step:
  • Line 2: we create a texture from a surface, given to us by the get_surface() function. As we've already said, a surface loads pixels into memory and stores them until we actually use them in a texture. This helper function (that resides in resources.h) retrieves the surface of an image already initialized in memory to avoid loading them again in memoy, wasting time and computing power. Every time a new image is created, if not already present inside the list, we append its surface to an unordered list whose key is the file path (since every file path is unique).

    • Fig 10. Better memory handling with surface preloading

  • Line 3 - Line 9: Check if we're given the dimensions. Since maybe we want to specify ourselves the size, and not let it be the effective size of the image, we can define the rect's width and height. Else, the SDL SDL_QueryTexture will retrieve the size of the image itself.
  • Line 10 - Line 11: Position the rect that will represent our image to its position.
  • Line 12: Find the center of the image. This will be helpful when we will add rotation.
  • Line 13: Color the image with the specified color.
